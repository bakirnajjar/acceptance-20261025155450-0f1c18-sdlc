## Risk register

### REA6D7-001 — Sign-in presentation or reset entry point diverges from the supplied wireframe

- **Priority/category:** should · presentation and entry. This is a planning judgment: a presentation or entry gap matters, but by itself does not establish a reset security failure.
- **Requirements:** [REQ-001](requirements_analysis.md), [REQ-002](requirements_analysis.md). **Evidence:** S, I, K.
- **Failure mode / impact:** The server-rendered sign-in card could lose a field label, `name@example.com` hint, masked password example, bordered card or heading; misplace the blue Forgot password? link beneath Password, dark Sign in button or administrator text; or fail to open the reset-request flow. Visitors would not recognize or reach specified recovery.
- **Mitigation / verification:** Compare rendered content and relative placement with the image and activate Forgot password? through to the request entry point. Do not infer login authentication, pixel dimensions or breakpoints.

### REA6D7-002 — Response parity or hourly request limit fails at account and threshold edges

- **Priority/category:** must · request handling. This is a planning judgment because parity and the five-per-account-per-hour limit are explicit ACC-STD-01 constraints, not an observed defect.
- **Requirements:** [REQ-003](requirements_analysis.md), [REQ-004](requirements_analysis.md). **Evidence:** K.
- **Failure mode / impact:** Existing/nonexistent-account reset responses could differ, especially at limit edges; a sixth request in an hour might be honored or a request among the first five might be blocked. This could reveal account existence or violate the requested limit/availability.
- **Mitigation / verification:** Compare otherwise equivalent responses, including the applicable threshold edge; check that eligible requests one through five are not stopped by the limit and a sixth in the hour is not honored. Preserve parity without assuming how nonexistent identifiers are counted or how the hourly window is implemented.

### REA6D7-003 — Reset link permits replay or violates the thirty-minute boundary

- **Priority/category:** must · reset links. This is a planning judgment because successful valid recovery, single use and expiration are explicit ACC-STD-02 behavior, not known faults.
- **Requirements:** [REQ-005](requirements_analysis.md), [REQ-006](requirements_analysis.md), [REQ-007](requirements_analysis.md). **Evidence:** S, K.
- **Failure mode / impact:** A valid unused link could fail before expiry; replay could change the password again; or an expired link might work at or after 30 minutes from issue. Legitimate recovery or link-use boundaries would be broken.
- **Mitigation / verification:** Exercise valid unused links before expiry, replay after a success, and completions just before versus at/after the 30-minute issue-time boundary with controlled time; confirm password changes only when permitted. A synthetic in-memory mechanism can expose links for tests without assuming external email or a specified URL format.

### REA6D7-004 — A successful reset leaves another active session signed in

- **Priority/category:** must · session invalidation. This is a planning judgment because all-session sign-out is an explicit ACC-STD-02 postcondition, not a known defect.
- **Requirements:** [REQ-008](requirements_analysis.md). **Evidence:** K.
- **Failure mode / impact:** Clearing only the submitting session could leave another active session signed in, defeating account-wide sign-out after recovery.
- **Mitigation / verification:** Establish multiple synthetic active sessions for one account, perform a successful reset, and check each previously active session is signed out. Do not require a complete login policy solely from the pictured button.

### REA6D7-005 — A successful reset lacks its own owner notification

- **Priority/category:** must · notifications. This is a planning judgment because each-success owner notification is an explicit ACC-STD-03 postcondition, not an observed delivery failure.
- **Requirements:** [REQ-009](requirements_analysis.md), [REQ-011](requirements_analysis.md). **Evidence:** S, K.
- **Failure mode / impact:** The in-memory sink could omit an owner record, associate it with the wrong synthetic account or record only one across multiple successful resets. An owner would lack a record for every success.
- **Mitigation / verification:** Complete separate successful resets and inspect the sink for an owner-directed notification per success. In-memory capture is not proof of external delivery.

### REA6D7-006 — Implementation constraints or production-limitations documentation drift

- **Priority/category:** should · architecture and limitations. This is a planning judgment about faithful delivery and interpretation, not a measured production or implementation condition.
- **Requirements:** [REQ-010](requirements_analysis.md), [REQ-011](requirements_analysis.md), [REQ-013](requirements_analysis.md). **Evidence:** S.
- **Failure mode / impact:** A different runtime/framework, client-rendered pages, real account/notification integrations or missing synthetic/in-memory production-limitations documentation could misrepresent the intended small demonstration as production-ready.
- **Mitigation / verification:** Inspect Python 3.12 target, Flask routes/server-rendered pages, synthetic account fixtures and in-memory sink; check documentation calls out synthetic and in-memory state/notification limits without imposing an exhaustive checklist.

### REA6D7-007 — Pytest checks miss the cross-cutting acceptance edges

- **Priority/category:** must · test coverage. This is a planning judgment because automated acceptance tests are an explicit deliverable; it is not a claim that tests were run or failed.
- **Requirements:** [REQ-012](requirements_analysis.md). **Evidence:** S, K.
- **Failure mode / impact:** Happy-path-only pytest checks could miss sign-in/entry fidelity, existing/nonexistent response parity, fifth/sixth request behavior, successful change, replay, the expiry boundary, multi-session sign-out or notification for each of several successes. An unmet acceptance criterion could go unnoticed.
- **Mitigation / verification:** Run pytest and map explicit checks to REQ-001 through REQ-009 and REQ-012, using synthetic accounts and controlled time as appropriate. Report any missing checks rather than assuming a passing suite.

### REA6D7-008 — Delivery accidentally includes deployment or deployment workflows

- **Priority/category:** must · scope control. This is a planning judgment because the exclusion is explicit, not evidence of any deployment.
- **Requirements:** [REQ-014](requirements_analysis.md). **Evidence:** S.
- **Failure mode / impact:** A release step, deployment or new deployment workflow could exceed the authorized demonstration scope.
- **Mitigation / verification:** Review the change list and execution record to confirm no deployment was performed and no deployment workflow was added; keep risk documentation and its checks local.

## Working assumptions and nonblocking questions

There is no approved implementation or test evidence; these are delivery uncertainties, not defect findings or likelihood scores. The `requirements_analysis` predecessor supplies identifiers, while S/I/K above supply factual evidence.

1. **A1, login scope:** Verify pictured controls and sign-out of synthetic active sessions without presuming a complete Sign in authentication policy. **Open (nonblocking):** Must the pictured button authenticate synthetic accounts, or is depicted UI plus session behavior sufficient?
2. **A2, counting:** Apply five requests per existing account per hour and account-existence response parity without prescribing nonexistent-identifier accounting or fixed versus rolling windows. **Open (nonblocking):** How should nonexistent identifiers be counted/limited while preserving identical responses, and what exact hourly-window algorithm applies?
3. **A3, visual fidelity:** Use observed labels, examples, card and relative placement without pixel/breakpoint targets. **Open (nonblocking):** What fidelity is needed at other viewport sizes, and must the examples be literal content?
4. **A4, link access:** An in-memory test mechanism can make issued links inspectable without external delivery or a mandated format. **Open (nonblocking):** How should an issued link be conveyed or inspected in the synthetic application?
5. **A5, password/docs:** Verify valid-link password change and document synthetic/in-memory production limits without adding complexity rules or an exhaustive production checklist. **Open (nonblocking):** Which exact password rules and production-limitations topics are expected?
